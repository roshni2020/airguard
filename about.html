AI is writing the code that drives robots next to airplanes.
AirGuard proves it's safe before it runs.

What the software does: it is an independent safety gate for autonomous airport ground robots. Every software update is red-teamed in a digital twin of the real San Francisco airport, judged against the FAA's own rules, and then either blocked and rolled back or deployed to the fleet.

Who it's for

Everyone who lets a robot near an aircraft

  • Airport operators (safety and operations teams). The FAA makes the airport operator responsible for every vehicle airside (AC 150/5210-20A §2). AirGuard gives them evidence before they approve an update.
  • Ground handlers running autonomous tugs, like the operations already live at Changi and Dubai, who need to know tonight's update won't put a tug into jet blast tomorrow.
  • Autonomous-vehicle vendors who ship frequent, increasingly AI-written updates and need a gate that isn't their own test suite.
  • Regulators, certifiers and insurers, who need reproducible, rule-cited proof rather than "trust us".
Why it matters

Fast software, physical consequences

Driverless baggage tractors already work beside aircraft at Singapore Changi and Dubai DWC, with trials at Amsterdam Schiphol and Stuttgart. Their software changes often, and more and more of it is written by AI.

  • The hazards are physical. A jet engine at idle can blow a vehicle over, and an aircraft pushing back cannot stop for a tug.
  • Reading the code is not enough. An AI diff reviewer rated our genuinely safe fix as unsafe (P(safe) = 0.055). It cannot see a hazard that only appears when the code runs next to a 777.
  • Testing on a live apron is dangerous and slow. The digital twin runs 1,000 scenarios in about a minute.
  • Trust is earned per update, and the decision is made by deterministic checks, not by another AI.
What the real data tells us

The danger is built into the airport

1. The FAA rulebook names the hazards.

"Avoid jet blast or prop wash, which can blow debris or overturn vehicles." (AC 150/5210-20A, App. B 2.2.1(c))
"Pay particular attention when aircraft beacons are illuminated, as they may be moving or preparing to move." (App. B 2.2.1(g))
"Don't assume that if the beacon(s) aren't flashing that the engine(s) isn't (aren't) running." (App. B 2.2.3)

The AC leaves speed limits to each airport, so there is no universal number. Every airport has to check updates against its own limits.

2. The real SFO map puts the hazard on the route. In the OpenStreetMap geometry, the service route along taxilane M5 between the A and B piers runs directly behind stand A7. When a 777 there starts its engines, its idle jet-blast zone (about 120 m) covers the road, and an ordinary delivery to A8 passes about 20 m inside it. That is the scene behind this text.

3. Aircraft size changes everything. From the FAA aircraft database: a 777-300ER is 73.9 m long with a 64.8 m span, against 37.6 m for an A320. Code that is safe next to an A320 can be unsafe next to a 777.

4. Fleets create new hazards. Across the whole airport (106 real stands, 3,206 buildings), 16 robots together produced 21 robot-to-robot close passes and 35 close passes to neighbouring aircraft that single-robot tests never see.

How it works

Agents propose. Python decides.

  • 1. An AI writes an update. Meta Muse Spark turns "make the route 20% faster" into controller code. Its output is sanitised before it ever runs.
  • 2. SubQ red-teams it. SubQ reads the full FAA AC, the SFO map, the code and every earlier 0.1 s trace (up to 676k tokens in one call), then designs harder scenarios each round. It never sees the implementer's reasoning.
  • 3. SubQ Snap screens and triages. It reads about 370k tokens of raw traces in seconds, rates severity and filters unrealistic tests. It is advisory only.
  • 4. A deterministic judge decides. The simulator runs every scenario on real SFO geometry, and fixed FAA-cited checks return PASS or BLOCK.
  • 5. Block or deploy. Unsafe updates are blocked and rolled back. Safe ones are promoted. Every verdict is hashed and reproducible.
  • 6. The gate improves itself. SubQ grows the test library, and a new version is adopted only if it catches more bad code on held-out tests without failing more good code.
